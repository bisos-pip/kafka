* Stage 2: Files over Kafka --- kafkaFileSend.cs / kafkaFileReceive.cs

<<Stage 2>>

Goal: a general-purpose, open facility to carry files through Kafka and rebuild them
exactly on the other side, developed and tested here against our own single-node
Kafka. This repo is public and generic: a consumer of these commands keeps its own plan,
notes and parameters in its own repository.

** The concept: records with headers, and an optional file model on top

Scope (user, 2026-10-14): *not a complete solution*. Lines of limited length, benevolent
senders. Known limits are listed at the end of this section so they are not rediscovered.

Two scopes are kept apart. =bisos.kafka= is a mechanism, externally public, with no knowledge of
any consumer: topic, key, header names, identity headers, markers and the output path are all
parameters. A consumer's needs are met by passing parameters; they live in the consumer's own
repository, never here.

*Records mode* --- the base. Each line of a file becomes one Kafka record:
- Value: the line, /without/ its terminator, exactly as in the file.
- Key and headers: parameters (=--msgKey=, =--headers k=v,...=). A consumer that knows nothing
  about files consumes these as ordinary rows, with their context in the headers.
- One transaction per file: a =read_committed= consumer sees all of a file or none of it.

*Files mode* --- optional, on top of records mode: the first and last record of a file carry one
extra header each, so a consumer /may/ rebuild the file. Rows-only consumers ignore them: the data
topic stays pure, there are no marker records.
- =kfx-bof= on the first record (JSON): =v=, =path=, =attrs=, =bytes=, =rows=, =sha256=, =eol=,
  =finalEol=, =idHeaders=, =hdr=. These are what the sender /declared/ (computed before sending).
- =kfx-eof= on the last record (JSON): =v=, =path=, =bytes=, =rows=, =sha256=. These are what the
  sender /observed/ while streaming. If observed differs from declared the file changed during
  the send and the sender aborts its own transaction.
- =path= is one logical, relative path with =/= separators (the last component is the file name),
  so the receiver can reproduce the hierarchy. =attrs= are free key-values for =--pathTemplate=.
- =idHeaders= names the headers whose values identify the file. The receiver demultiplexes
  interleaved files (concurrent senders share a partition) by those values; no per-record id.
- =eol= and =finalEol= let the receiver rebuild the exact bytes although values carry no terminator.
- =hdr= says how headers are encoded: =kafka= (record headers, the only mode built). A later
  =prefix= mode (fields inside the value, with a delimiter) can be added without changing the format.
- Why both markers when transactions exist: a consumer left at the default
  =isolation.level=read_uncommitted= sees open and aborted transactions; a BOF with no EOF
  tells it the file is incomplete.

*Receiver* (files mode only; refuses records-mode data): buffers per file until EOF, verifies rows,
bytes and SHA-256 against both markers, checks the path (relative, no =..=), writes atomically
(temporary name, then rename) under =--outBase=. Same path and same hash: skipped. Same path,
different hash: replaced atomically (=--onExists replace|fail|skip=). Optional =--latest NAME=
points a symlink at the newest directory. Offsets are committed only up to the oldest still-open
file, so a crash re-reads unfinished files.

*Why build it*: nothing standard does this. =kcat= sends lines and prints records, with no file
boundaries, atomicity or verification. Kafka's =FileStreamSource= / =FileStreamSink= are demo
connectors (believed off the default plugin path since Kafka 3.2) and keep no boundaries. Spooldir /
FilePulse ingest files with metadata, but nothing rebuilds them at the other end. S3 / HDFS sinks do
not rebuild the producer's exact file per batch. Whole-file transfer over Kafka is usually steered to
SFTP / S3 or a claim check.

*Post after the file is complete, not line by line as produced* (decided 2026-10-12 in the first
use case): avoids publishing before validation, avoids transactions open for minutes against the
60 s default timeout, and keeps producing the file independent of broker health.

*Known limits (by decision)*: lines only (no chunking of binary files or huge lines); one uniform
line terminator per file; non-empty files only; a file is held in memory by sender and receiver;
two simultaneous sends of the same identity are not separated; a sender killed mid-transaction
stalls =read_committed= readers of that partition until =transaction.timeout.ms= (default 60 s);
path checking is against mistakes, not against a hostile sender; no tree manifest (a =set= attribute
is reserved for one).

** Placement and packaging (decided 2026-10-12, user)

- The logic: =py3/bisos/kafka/kafkaFileTransfer.py=, a pure module that imports
  only the Kafka client. (=bisos/kafka/__init__.py= is empty, so it pulls in
  nothing else at import.)
- The Cmnd classes =fileSend= and =fileReceive=: =py3/bisos/kafka/kafkaFileTransfer_csu.py=,
  over the pure module.
- The commands: =kafkaFileSend.cs= and =kafkaFileReceive.cs= in =py3/bin/=, two thin
  files that load that one csu, each with its own parameters, readme and examples. Named
  Send and Receive (user, 2026-10-14): /source/ and /sink/ are Kafka Connect words and
  clash with the "source" attribute that data records commonly carry ("where the data came from"). One implementation, not
  one file dispatching on =$0= (user's decision: no invocation-name magic).
- *pipx, not pip --- how BISOS stays out of the user's runtime*: installing with
  pipx is like =apt-get=: consumers get executables in an isolated venv and take
  on nothing at the library level. A consumer's code runs the commands as
  subprocesses, by name or path, and never imports =bisos.kafka=. =bisos.kafka='s
  full =install_requires= (=bisos.b=, =banna=, =capability=, =sbom=, =debian=,
  =webCap=, ...) lands in pipx's private venv, which is acceptable at that level.
  Considered and set aside: making the provisioning dependencies an optional
  extra, or splitting the module into its own package.
- Parameters --- generic (none is specific to any consumer; =--clientConf= carries security settings):
